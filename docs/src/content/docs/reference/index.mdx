Reference pages collect durable facts that readers need to find quickly: data contracts, policies, workflow inventories, path maps, and compatibility notes. They are intentionally less narrative than operator or developer guides.

## Reference categories

| Category | Examples |
| --- | --- |
| Contracts | FlatBuffers schemas, API shapes, authentication/session invariants, watch-state semantics. |
| Workflow policies | SQLx offline metadata rules, dynamic query exceptions, visual QA evidence, codegen steps. |
| Path maps | Where server, player, mobile, packaging, and generated files live in the repository. |
| Compatibility notes | Platform support, playback backend tradeoffs, Android/TV recovery expectations. |
| Existing docs inventory | Markdown files already in `docs/` that remain useful while they are converted into Starlight pages. |

## When to use a reference page

Use a reference page when the reader needs a stable answer more than a tutorial. If the page mainly tells a reader how to complete a task, it belongs in an operator, developer, or release section and can link back here for definitions.
