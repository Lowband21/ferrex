The developer guide explains how to change Ferrex with confidence. It should connect architecture decisions to the commands and files that keep the Rust server, desktop player, Android clients, and generated contracts consistent.

## Development lanes

| Lane | What the guide should cover | Current source material |
| --- | --- | --- |
| Repository setup | Nix shells, Rust toolchain, local services, and contribution workflow. | `.github/CONTRIBUTING.md`, `flake.nix`, `justfile` |
| Backend and core | Crate responsibilities, database expectations, scanner/watch-state behavior, and compile-checked SQLx policy. | `docs/architecture.md`, `docs/sqlx-postgres-workflow.md`, `docs/sqlx-dynamic-query-allowlist.md` |
| Desktop player | UI architecture, visual QA, playback backends, and player crate boundaries. | `docs/ui-testing-workflow.md`, `docs/player-dependency-boundaries.md` |
| Android and TV | Shared contracts, recovery-sensitive client state, emulator QA, and lint/test commands. | `mobile/`, `docs/mobile-device-auth-flatbuffers.md`, QA notes |
| Generated contracts | FlatBuffers schemas, generated Kotlin, and compatibility expectations. | `mobile/shared/`, generation scripts |
| Validation | Focused commands for the part of the tree touched by a change. | `justfile`, CI workflows, issue-specific QA notes |

## Command documentation standard

Commands should be copied exactly as maintainers run them. When a command depends on Nix, Android SDK paths, a database, or a generated metadata cache, document that dependency next to the command rather than burying it in prose.

## Architecture documentation standard

Architecture pages should name the owning crate or module, the data it reads or writes, and the boundary it enforces. If a page introduces a new abstraction, it should also name the validation that prevents that boundary from drifting.
